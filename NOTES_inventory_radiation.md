# Радиация от артефактов в инвентаре (рюкзаке) — техническая записка

Составлено 08.10.2026 после того, как попытка реализовать механику скриптом
привела к поломке контейнеров. Записка нужна, чтобы механику можно было
**переписать с нуля**. Все факты ниже проверены по исходникам движка IX-Ray
(пути и номера строк указаны) либо по логам игры.

---

## 1. Что именно требуется (постановка от заказчика)

1. Артефакты, лежащие **в инвентаре (рюкзаке)**, должны облучать актора так же,
   как лежащие **на поясе**. То есть паритет, без дополнительных множителей.
2. **Костюм не учитывается** — в точности как для пояса (обоснование в разделе 4).
3. Контейнеры: комбо-предмет «артефакт в контейнере» — тоже артефакт, но его
   `radiation_restore_speed` **уже уменьшен контейнером** на этапе конфига
   (`max(0, радиация артефакта − поглощение)`, поглощение 0.004 / 0.008 / 0.014).
   Отдельного кода для комбо не нужно: они попадают в общий перебор.
   Следствие: у научного контейнера остаток обычно 0, поэтому в рюкзаке он
   «не фонит» — это и есть его смысл.
4. Что НЕ делаем: износ артефактов и контейнеров на радиацию не влияет;
   NPC, трупы, ящики, предметы на земле не считаем — только инвентарь актора.

## 2. Как это работает для ПОЯСА (эталон, реализовано в движке)

`CActor::UpdateArtefactsOnBelt` — `src/xrGame/Actor.cpp:2608-2630`.

Каждый кадр движок перебирает **только пояс** (`inventory().m_belt`):

```cpp
for (const PIItem item : inventory().m_belt)
    if (CArtefact* artefact = item->cast_artefact())
    {
        float art_cond = artefact->GetCondition();     // износ (0..1)

        conditions().ChangeBleeding((artefact->m_fBleedingRestoreSpeed * art_cond) * f_update_time);
        conditions().ChangeHealth  ((artefact->m_fHealthRestoreSpeed   * art_cond) * f_update_time);
        conditions().ChangePower   ((artefact->m_fPowerRestoreSpeed    * art_cond) * f_update_time);
        conditions().ChangeSatiety ((artefact->m_fSatietyRestoreSpeed  * art_cond) * f_update_time);
        conditions().ChangeThirst  ((artefact->m_fThirstRestoreSpeed   * art_cond) * f_update_time);

        if ((artefact->m_fRadiationRestoreSpeed * art_cond) > 0.0f)
        {
            float val = (artefact->m_fRadiationRestoreSpeed * art_cond)
                      - conditions().GetBoostRadiationImmunity();
            clamp(val, 0.0f, val);
            conditions().ChangeRadiation(val * f_update_time);
        }
        else
            conditions().ChangeRadiation((artefact->m_fRadiationRestoreSpeed * art_cond) * f_update_time);
    }
```

**Формула радиации для пояса:**

```
за кадр:  ChangeRadiation( max(0, radiation_restore_speed * condition − boost_radiation_immunity) * dt )
```

Где `dt` (`f_update_time`) — время кадра в **секундах**.

Важные следствия:

* Единица измерения — «сырое» значение конфига. В интерфейсе показ
  = значение × 1000 (см. `ActorCondition.cpp`, `UIHudStatesWnd`).
* Вычитается **только** `GetBoostRadiationImmunity()`. Это **временный буст от
  препаратов** (`boost_radiation_immunity`, `EntityCondition.cpp:700`), а НЕ
  защита костюма. Защита костюма (`radiation_immunity` в `immunities_sect`) в
  этой формуле вообще не участвует.
* В оригинальном `outfit.ltx` у всех костюмов и шлемов
  `radiation_immunity = 0.0`, то есть даже если бы участвовала — эффекта нет.
* `boost_radiation_immunity` из Lua **недоступен** (биндинга нет). При
  реализации скриптом им пренебрегаем — это осознанное упрощение.

Пояс: `m_belt` — `Inventory.h:129`; рюкзак — `m_ruck`.

## 3. Чего в движке НЕТ

Движок **не** облучает артефакты в рюкзаке: цикл в `Actor.cpp:2608` идёт
строго по `m_belt`. Поэтому механику надо либо дописать скриптом, либо
изменить движок (раздел 7).

## 5. Вариант реализации СКРИПТОМ (набросок)

Логика:

1. Раз в `STEP` мс (предлагалось 300 мс) накопить прошедшее время по
   `time_global()`.
2. Пройти `actor:iterate_inventory`, пропуская предметы на поясе
   (`actor:is_on_belt(item)`) — их уже обработал движок.
3. Для каждого предмета взять `get_artefact_radiation()` (в `pcall`),
   просуммировать положительные значения.
4. `actor:change_radiation(sum * FACTOR * seconds)`, где `FACTOR = 1.0` для
   паритета с поясом.

Обязательные предосторожности (без них будут баги, уже проверено):

* **Дельта времени через `time_global()`**, а не «один тик = фиксированный
  шаг»: обработчик может вызываться несколько раз за кадр.
* **Ограничивать дельту** (например, 1000 мс). После загрузки сейва метка
  времени «рвётся», и без ограничения первый тик начислит огромную дозу.
  Плюс сбрасывать накопленное время в обработчике `load`.
* Не менять радиацию, если `sum <= 0` (иначе лишние вызовы каждый тик).
* `get_artefact_radiation` — только в `pcall`: на не-артефакте он бросает.

## 6. КРИТИЧНЫЕ ГРАБЛИ (из-за них механика и сломала контейнеры)

### 6.1. Реестр колбэков поддерживает МНОГО подписчиков

`gamedata/scripts/ixray_system/dynamic_callbacks.lua`:

```lua
local intercepts = { save = {}, load = {}, update = {}, save_state = {}, load_state = {} }

function RegisterScriptCallback(name, func_or_userdata)
    if (intercepts[name]) then
        intercepts[name][func_or_userdata] = true      -- ДОБАВЛЯЕТ в таблицу
    end
end

function SendScriptCallback(name, ...)
    for func_or_userdata, v in pairs(intercepts[name]) do
        func_or_userdata(...)                          -- вызывает ВСЕХ
    end
end
```

**Вывод: подписываться на `update` можно многократно.** Утверждение
«при двух подписчиках рассылка перестаёт доходить» — **неверно**.
Более того, на `update` штатно подписаны и другие скрипты аддона:

```
bq_quest.script:239        RegisterScriptCallback("update", update)
bq_stash_quest.script:564  RegisterScriptCallback("update", update)
```

Кто рассылает: `bind_stalker.script:384` → `SendScriptCallback("update")`,
в самом конце `actor_binder:update()`, то есть **каждый кадр**.

### 6.2. Состояние НЕЛЬЗЯ держать в локальных переменных модуля

Движок исполняет `.script` **повторно** в течение одной сессии. В логе видно
две записи `* loading script bq_containers.script` за сессию. Это не
«перезагрузка»: `process_file_if_exists` уже загруженный модуль не
перезагружает (`src/xrScripts/script_engine.cpp:321`, проверка
`namespace_loaded`). Значит создаётся **новый экземпляр модуля**, и все его
`local`-переменные — новые.

Чем это ломается:

* флаг вида `local hooked = false` сбрасывается → повторная регистрация
  обработчика (безвредно, но бессмысленно);
* **разделяемое состояние расщепляется**: обработчик из нового экземпляра
  пишет в свой `pending`, а `apply_pending` старого экземпляра видит свой
  `pending = nil` и ничего не делает. Замена предметов не применяется никогда.

**Правило: разделяемое состояние — только в `_G`** (например,
`_G.bq_containers_state = { pending = ..., hooked = ..., listeners = ... }`).
Для того, что должно переживать сохранение — `pstor` / инфопорции.

### 6.3. Подписка на `update` МОЖЕТ ПОТЕРЯТЬСЯ — и это не лечится флагом

Наблюдение из игры: обработчик `update` вызывается **ровно один раз**, дальше
тишина, при этом игра работает нормально и игрок активно действует. То есть
подписка теряется на стороне движка.

Косвенное подтверждение: запись «скрипт загружен, диспетчер установлен»
появляется только в начале сессии, а не при каждой загрузке уровня — значит
модуль исполняется повторно, но `on_game_start()` уже не отрабатывает (флаг в
`_G`), и если реестр колбэков к этому моменту пересоздан, подписка теряется
навсегда.

**Как это лечат соседние скрипты аддона:** `bq_quest.script:246-249` —

```lua
-- Serialized task functors reload this module after a Lua VM restart.
function poll_task()
    on_game_start()      -- перерегистрация колбэков
    return false
end
```

**Вывод для переписывания:** регистрацию делать **идемпотентной функцией** и
вызывать её из всех точек, которые движок разрешает по имени при действии
игрока (например, `on_game_start`, обработчик перетаскивания, обработчик
«достать артефакт»). Повторная подписка безвредна (см. 6.1).

### 6.4. Обработчики Lua не защищены от ошибок

`SendScriptCallback` — обычный цикл `pairs` без `pcall`. Если **любой**
подписчик бросит ошибку, исключение прервёт `SendScriptCallback`, и остальные
подписчики в этом кадре не выполнятся. Поэтому внутри обработчика `update`
свою логику оборачивать в `pcall`.

### 6.5. Совпадение имён глобальных функций

`bq_quest.script:212` и `bq_stash_quest.script:515` **оба** объявляют
глобальную `function update()`. В Lua глобальная одна, поэтому
`bq_stash_quest` (загружается позже) затирает функцию квеста документов, а на
`update` зарегистрирована именно она. Следствие: пофреймовая логика
`bq_quest.update()` не выполняется вообще. **Давать функциям уникальные имена**
(`bq_quest_update`, `bq_inv_rad_update`).

### 6.6. Отладка

`log()` из скриптов аддона **в игровой лог не попадает** — писать в свой файл
в корне игры через `io.open(path, "a")` (см. MEMO 13.5).

## 7. Альтернатива: правка движка

Цикл по артефактам — `src/xrGame/Actor.cpp:2608`. Можно добавить второй цикл
по `inventory().m_ruck` с той же формулой. Плюсы: точный паритет, нет

принципиально работает **без** правки движка — см. README и MEMO 24).

## 8. Что именно сломалось в прошлый раз (итог)

1. Ввели единый «диспетчер обновления» в `bq_containers.script` и подключили к
   нему модуль радиации. Заодно переписали регистрацию на `on_tick`.
2. Разделяемое состояние (`pending`, `hooked`, список подписчиков) осталось в
   **локальных** переменных модуля → при повторном исполнении модуля
   расщепилось (см. 6.2). Итог: вложение артефакта перестало превращаться в
   комбо, а достать предмет обратно стало нечем — у пустого контейнера нет ни
   `use1_functor`, ни комбо-секции. Внешне: «положил, комбо не появилось».
3. Перенос состояния в `_G` починил первую замену, но всплыл следующий
   уровень: подписка на `update` теряется, обработчик вызывается один раз за
   сессию (см. 6.3). Взаимодействие с контейнерами после этого не работает.
4. Радиация к этой поломке отношения не имела — но `bq_inv_rad.script` был
   подключён из `bq_containers.on_game_start()`, то есть связывал две
   независимые механики. **При переписывании делать их независимыми.**

## 9. Чек-лист перед запуском переписанной версии

- [ ] Разделяемое состояние — в `_G`, не в локалах модуля.
- [ ] Регистрация колбэка идемпотентна и вызывается при каждом действии игрока.
- [ ] Своя логика в `update` обёрнута в `pcall`.
- [ ] Имена глобальных функций уникальны (нет второй `update`).
- [ ] Дельта времени через `time_global()`, ограничена сверху, сбрасывается на
      `load`.
- [ ] `get_artefact_radiation()` вызывается только в `pcall`.
- [ ] `iterate_inventory` не возвращает `true` (иначе перебор оборвётся).
- [ ] Механика радиации **не** подключена из скрипта контейнеров.
- [ ] Проверить в игре: радиация в рюкзаке начисляется; вложение и доставание
      артефакта работают до и после загрузки сейва.
