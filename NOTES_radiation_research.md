## 1. Как движок грузит скрипты аддона (проверено, это была первая грабля)

Движок **не сканирует папку `scripts`** и не исполняет файлы подряд.

1. `CScriptEngine::setup_auto_load` — `src/xrScripts/script_engine.cpp:168-190`:
   один раз перечисляет `$game_scripts$` и заполняет реестр `xray_scripts`
   (имя файла без пути и расширения → полный путь).
2. Дальше скрипт исполняется **только по обращению по имени**:
   * `CScriptEngine::function_object` — `script_engine.cpp:381-398`: разбирает
     строку `"имя_скрипта.функция"` и вызывает `process_file("имя_скрипта")`.
     Именно так движок достаёт **всё, что прописано в конфигах**:
     `script_binding`, `OnItemDropped`, `OnKeyPress`, `use1_functor` и т.п.
   * метатаблица `auto_load` — `script_engine.cpp:128-149`;
   * `prefetch("имя_скрипта")` — биндинг `script_engine_script.cpp:85-88`, `:339`.

**Практический вывод:** новый скрипт аддона обязан быть упомянут по имени либо
в конфиге, либо в другом уже загруженном скрипте. Файл, лежащий в `scripts\`,
сам по себе не работает.

### Точка входа `addon.init` (`script:`) в этой сборке СЛОМАНА

Документация IX-Ray (`docs\docs\main\ru\addon-system\general-information.md:18-33`)
описывает ключ `script:`. Но разбор в `CAddonManager::ReadMetaInfo`
(`src/xrCore/xrAddons.cpp:79-94`) содержит **перевёрнутые сравнения**:

```cpp
if (NameEntryIndex == xr_string::npos)   // должно быть !=
    { ... NewAddon.AddonName = ...; }
if (ScriptEntryIndex == xr_string::npos) // должно быть !=
    return;
```

Поэтому ни `name`, ни `script` не читаются. Ни один аддон сборки этим не
пользуется. **Полагаться нельзя.**

## 2. Как работает радиация на поясе (эталон, чистый C++)

`CActor::UpdateArtefactsOnBeltAndOutfit` — `src/xrGame/Actor.cpp:2591-2641`.
Вызывается **каждый тик планировщика** из `CActor::shedule_Update`
(`Actor.cpp:2013`, вызов на строке **2236**). Внутри — свой аккумулятор:
пересчёт раз в `ARTEFACTS_UPDATE_TIME = 0.100f` (строка 2589):

```cpp
for (const PIItem item : inventory().m_belt)          // :2608 - ТОЛЬКО пояс
    if (CArtefact* artefact = item->cast_artefact())
    {
        float art_cond = artefact->GetCondition();
        ...
        if ((artefact->m_fRadiationRestoreSpeed * art_cond) > 0.0f)
        {
            float val = (artefact->m_fRadiationRestoreSpeed * art_cond)
                      - conditions().GetBoostRadiationImmunity();
            clamp(val, 0.0f, val);                    // :2622 - это ограничение СНИЗУ
            conditions().ChangeRadiation(val * f_update_time);
        }
        else
            conditions().ChangeRadiation((artefact->m_fRadiationRestoreSpeed * art_cond) * f_update_time);
    }
```

**Важно:** `clamp(val, 0.0f, val)` — не ограничение сверху. У `clamp(value,min,max)`
при `min > max` результат равен `max`, то есть `val`. Значит это `max(0, val)`,
ограничение **снизу**, и оно срабатывает только при `boost > 0`.

`boost_radiation_immunity` из Lua **недоступен** (биндинга нет). Берём его
минимальное значение `0` — тогда вклад пояса равен `radiation × condition`
**без каких-либо ограничений**, и рюкзак надо считать ровно так же.

### Скедулер — это и есть кадровый механизм (важно для раздела 5)

`CActor::shedule_Update` (`Actor.cpp:2013`) первым делом вызывает
`inherited::shedule_Update(DT)` (`:2026`), то есть `CGameObject::shedule_Update`
(`GameObject.cpp:811`), а тот — `CScriptBinder::shedule_Update(dt)` (`:825`),
а тот — Lua-метод **`update`** биндера:
`luabind::call_member<void>(this,"update",time_delta)`
(`script_binder_object_wrapper.cpp:84-87`).

**Вывод:** Lua-метод `update` биндера и радиация на поясе висят на ОДНОМ
механизме — планировщике. Если объект получает `shedule_Update`, его биндер
получает `update`. Именно поэтому в Anomaly биндер артефакта успевает
обрабатывать рюкзак.

**Что требуется проверить:** получает ли `shedule_Update` предмет, лежащий
**внутри инвентаря актора**. Актор — получает (это доказано). Про предметы в
рюкзаке прямого доказательства у меня нет: предметы в инвентаре переходят в
offline, и планировщик может их не обрабатывать. Это ключевой вопрос для
маршрута из раздела 5.

### Готовый расчёт, который НЕ доступен из Lua

`CActor::GetRestoreSpeed(ALife::eRadiationRestoreSpeed)` —
`Actor.cpp:2838`, ветка радиации `:2863-2877` — суммирует
`m_fRadiationRestoreSpeed * GetCondition()` по `m_belt` плюс костюм.

**Из Lua он не экспортирован.** Проверено: `GetRestoreSpeed` встречается только
в `Actor.h:856`, `Actor.cpp:2838`, `game_expression_delegates.cpp:124`,
`UIActorStateInfo.cpp:129,286`. Ни одного биндинга. Взять из Lua сумму по поясу
нельзя — но она и не нужна, пояс считает движок.

## 3. ГЛАВНАЯ НЕРЕШЁННАЯ ПРОБЛЕМА: рассылка `update` не доходит

### Что установлено по логам заказчика

* `bq_inv_rad.log`, сессия 15:02: `ДИАГ: радиация tick=1` в 15:02:38 и больше
  **ни одной строки** за 25 секунд игры. Диагностика пишет раз в 5 секунд по
  таймеру, то есть при работающей рассылке строк было бы ~5.
* `bq_containers.log`, та же сессия: `apply_pending` **не вызывался ни разу**
  (нет строки `ДИАГ: контейнеры tick=`, которая печатается на первом вызове).
* При этом `on_item_dropped` работает (движок вызывает его напрямую из C++).
* Игровой лог **чист**: ни одной ошибки Lua, ни `[LUA]`, ни `FATAL`.

### Механизм рассылки

`bind_stalker.script:384` — `SendScriptCallback("update")`, **в самом конце**
`actor_binder:update(delta)`. Ранние выходы — только `-designer` (`:248`) и
прыжок уровня (`:252`); ни то, ни другое в игре заказчика не выполняется.

Сам реестр — `gamedata\scripts\ixray_system\dynamic_callbacks.lua`:

```lua
local intercepts = { save = {}, load = {}, update = {}, save_state = {}, load_state = {} }

function RegisterScriptCallback(name, func_or_userdata)
    if (intercepts[name]) then
        intercepts[name][func_or_userdata] = true      -- ДОБАВЛЯЕТ
    end
end

function SendScriptCallback(name,...)
    if (intercepts[name]) then
        for func_or_userdata,v in pairs(intercepts[name]) do
            if (type(func_or_userdata) == "function") then
                func_or_userdata(...)                  -- вызывает ВСЕХ
            elseif (func_or_userdata[name]) then
                func_or_userdata[name](func_or_userdata,...)
            end
        end
    end
end
```

**Реестр — это ЛОКАЛЬНАЯ таблица.** Она создаётся при исполнении
`dynamic_callbacks.lua`, а этот файл грузится **из C++**:
`LoadScriptToGlobal(L, "dynamic_callbacks.lua")` —
`src/xrScripts/lua_ext.cpp:230`, из `lua_init_ext` (`:219`), а тот — из
`CScriptStorage::reinit()` (`src/xrScripts/script_storage.cpp:48-81`), внутри
которой `lua_close(m_virtual_machine)` и **новый** `luaL_newstate()`.

**Значит при каждом пересоздании Lua-машины реестр обнуляется, а подписки,
сделанные до этого, остаются в мёртвой таблице.** В игровом логе это видно как
**двойная загрузка `_g`** (строки 171 и 243).

### Где вызывается пересоздание машины

`CScriptEngine::init()` (`script_engine.cpp:193-240`) начинается с
`CScriptStorage::reinit()` (`:195`) и заканчивается `process_file_if_exists("_g")`
(`:209`). `init()` вызывается:

1. `src/xrGame/ai_space.cpp:62` — старт движка;
2. `src/xrGame/alife_simulator.cpp:45` — из `restart_all()`, вызываемого
   конструктором `CALifeSimulator` (`:58`).

Наблюдение из логов: обе загрузки `_g` происходят **до** загрузки наших скриптов
(строки 171/243 против 413/425), то есть в момент нашей регистрации реестр уже
должен быть стабилен. **Это противоречит наблюдению «подписка не работает» — и
именно это противоречие надо разрешить.**

### Что исключено проверкой

* **Копий наших скриптов без аддона нет** — `gamedata\scripts\bq_*` пусто.
* **Других подписчиков `update` в сборке нет**: `RegisterScriptCallback("update"`
  не встречается ни в `gamedata`, ни в аддонах.
* **Коллизий имён нет**: `on_key_press`, `on_can_move_to_partner`,
  `on_item_focus`, `on_item_dropped` в сборке больше никто не объявляет.
* `UnregisterScriptCallback` в сборке **не вызывается нигде** — значит
  отписки извне быть не может.

**Отсюда:** остаются только два объяснения, и их надо различить экспериментом:
(а) наша регистрация попадает в таблицу, которую потом заменяют;
(б) `lua_close`/`luaL_newstate` переиспользует старый `_G`, и `intercepts`
«залипает» между машинами, из-за чего `RegisterScriptCallback` пишет в мёртвую
таблицу. Вариант (б) косвенно подтверждается тем, что записи в `bq_inv_rad.log`
**накапливались между сессиями** (в файле лежали строки от 13:47, 14:30, 14:43,
14:54, 15:02).

## 5. Как сделано в Anomaly (референс) и почему это может не подойти

Файл: `Stalker_Anomaly\tools\_unpacked\scripts\item_artefact.script`.

* Радиация из рюкзака — `:440-461`, ветка `artefact_binder:update(delta)`:
  ```lua
  elseif (tg > self._tmr_rad) and (not self.no_rad) and in_actor_ruck(obj) then
      self._tmr_rad = tg + rad_tg_step          -- 300 мс
      local rad_val = cobj.m_fRadiationRestoreSpeed or 0
      db.actor:change_radiation(rad_val * rad_factor)   -- rad_factor = 0.5
  ```
  То есть **не сумма по рюкзаку**, а по artefact-объекту: каждый артефакт сам
  начисляет свою дозу со своим таймером. Множитель `0.5`, шаг 300 мс.
* `in_actor_ruck(obj)` — `utils_item.script:678`:
  `in_actor_inv(obj) and (not db.actor:is_on_belt(obj))`. Ровно то правило,
  которое мы и хотим.
* Радиация применяется через `change_radiation`, а не через запись значения.
* Биндер вешается на секцию артефакта: `script_binding = item_artefact.bind` —
  `configs\items\items\items_artefacts.ltx:88` (и `:1569`, и
  `items_artefacts_soc.ltx:30`). В нашей сборке то же самое делает `af_base`
  (`script_binding = bind_artefact.bind`), и у нас есть **свой**
  `bind_artefact.script` в оригинальной gamedata.

**Ключевой вопрос, который надо проверить в игре:** вызывается ли
`artefact_binder:update` для артефактов, лежащих **в инвентаре актора**
(а не на земле). В нашей `bind_artefact.script` метод `update` есть, но первая
же проверка `self.first_call` работает с `get_physics_shell()` — у инвентарных
предметов физшелла нет. Если движок всё же зовёт `update` для инвентарных
объектов, то **это и есть самый надёжный маршрут**: он не зависит от реестра
колбэков вообще.

Устройство биндера (проверено):
* `CScriptBinderObject::shedule_Update(u32)` — `script_binder_object.h:33`;
* Lua-метод называется `update`: `luabind::call_member<void>(this,"update",time_delta)`
  — `script_binder_object_wrapper.cpp:84-87`;
* кадровый вызов: `CGameObject::shedule_Update` → `CScriptBinder::shedule_Update`
  — `GameObject.cpp:811-826`;
* биндер вешается через `script_binding`, который разрешается в
  `CScriptBinder::reload` — `script_binder.cpp:61-98`
  (`ai().script_engine().functor(...)` + вызов с игровым объектом);
* обёртки биндера оборачивают вызов в `try/catch` и при ошибке `clear()`.

### Как это применить в нашей сборке (вариант, требующий проверки)

Нужен объект, который **гарантированно получает `shedule_Update` каждый кадр** и
на который можно повесить `script_binding = наши_скрипт.bind`. Ограничения:

* на акторе слот биндера **занят** — `bind_stalker.bind` (иначе сломается весь
  биндер актора: `db.actor`, сейвы, инвентарь). Переопределять нельзя;
* значит нужен **свой объект**, который спавнится на уровне и живёт постоянно.
  Кандидаты: `space_restrictor` (в аддоне уже есть
  `bq_beard_marker` / `bq_sich_marker`) либо отдельная пустая секция,
  заспавненная на старте уровня. Ни один из них в аддоне сейчас не спавнится
  автоматически — это надо решать.

**Проверять это надо экспериментом**, а не рассуждением: повесить
`script_binding` на объект, который точно спавнится (через debug-спавнер), и
посмотреть, идут ли вызовы `update` в лог.

## 6. Звук ошибки Windows при открытии инвентаря — НЕ ОБЪЯСНЁН

Что проверено:

* В игровом логе **ошибок нет** вообще (искал `error`, `Error`, `FATAL`,
  `[LUA]`, `assert`, `stack` — чисто, кроме безобидных DLTX-предупреждений
  чужого аддона HQ Icons).
* Единственное место в сборке, откуда из скриптов может прозвучать системный
  звук, — `trigger_assert` (`src/xrScripts/script_engine_script.cpp:58-68`):
  в release-сборке он вызывает `MessageBoxA(..., "Report to wh1t3lord, because
  xr_parser failed...")`.
* **Но вызовов `trigger_assert` в скриптах сборки НЕТ** (проверено поиском по
  `gamedata` и по аддонам). Файла `xr_parser` в сборке тоже нет.
* Обработчик ошибок luabind `lua_pcall_failed`
  (`script_engine.cpp:70-83`) печатает стек и вызывает `on_error`, но
  `Debug.fatal` под `#if !XRAY_EXCEPTIONS` — при включённых исключениях его нет.

**Гипотеза (не подтверждена):** звук издаёт движок при ошибке Lua, которую он
ловит и печатает не в файл, а только в консоль/на экран. Тогда «игра не вылетела
и сообщения не было» объясняется тем, что сообщение ушло в debug-оверлей ImGui
или было подавлено.

**Как различить (предлагаю):** это надо проверить экспериментом, а не догадками.
Самый дешёвый способ — временно убрать все наши скрипты из конфига колбэков
(`[callbacks]`), оставив только `OnItemDropped`, и посмотреть, пропадёт ли звук.
Если пропадёт — источник в наших точках входа; если останется — звук не наш.

**Важная зацепка:** звук появился в сборке `b786b6c` (там контейнеры работали)
и связан **с открытием инвентаря**. При открытии инвентаря срабатывает ровно
один наш колбэк — `OnItemFocusReceive = bq_containers.on_item_focus`, который
вызывает `RegisterScriptCallback("update", apply_pending)`.
**Подозрение: это `MessageBoxA` от `R_ASSERT2` в `UIActorMenu_action.cpp:350`**
(«failed to get OnItemFocusReceive functor»), если движок в какой-то момент не
может разрешить функцию. Проверяется тем же экспериментом с отключением ключа.

## 7. Предложенный заказчиком вариант: разбор

Идея: держать таблицу «секция → радиация за штуку», при изменении инвентаря
(подбор/выброс) и при открытии инвентаря пересчитывать сумму по рюкзаку и
применять её к актору.

**Что в этом хорошо:**
1. Таблица снимает главную опасность — не нужен `iterate_inventory` на каждом
   кадре и вообще разбор живых объектов. Значит уходит и риск вылета, который
   был 08.10 (вылет случался именно в расчёте, а не в регистрации).
2. Пересчёт «по событию» вместо «каждый кадр» дешевле и понятнее.
3. Итог всё равно применяется через `change_radiation` — то есть тем же
   способом, что и пояс, и так же накопительно.

**Что надо решить (это вопросы, а не возражения):**
1. **Момент применения.** `update` не работает (раздел 3), а таблицу надо
   применять во времени. Варианты: (а) начислять «пачкой» в те моменты, когда
   нас и так зовёт движок (`on_item_dropped`, `OnItemFocusReceive`); (б) найти
   надёжный кадровый хук (биндер — раздел 5). Вариант (а) проще и не требует
   кадрового хука, но доза будет приходить рывками при взаимодействии с
   инвентарём, а не ровно.
2. **Откуда берётся «радиация за штуку».** Проще всего из конфига
   (`radiation_restore_speed` секции) — но тогда нужен доступ к конфигу, а не
   `get_artefact_radiation()`. `system_ini():r_float(section, "radiation_restore_speed")`
   работает и не бросает исключений — это надёжнее, чем `get_artefact_radiation`.
   Минус: не учитывается износ (`condition`). Для рюкзака это, возможно, и не нужно.
3. **Подсчёт количества.** «2 штуки af_eye» — это две отдельные записи в

4. **Комбо-версии.** Их `radiation_restore_speed` уже уменьшен контейнером на
   этапе конфига, поэтому они попадают в ту же таблицу автоматически —
   отдельного кода не нужно.
5. **Открытие инвентаря** как триггер пересчёта — доступно через
   `OnItemFocusReceive` (движковый колбэк, работает).

## 8. Что предлагаю проверить в игре, прежде чем писать код

Все пункты дешёвые и дают однозначный ответ.

1. **Работает ли `update` вообще.** Взять `bq_containers.script` в текущем виде
   (он уже пишет `ДИАГ: контейнеры tick=` раз в 5 секунд) и просто поиграть
   минуту, ничего не делая. Строки есть → рассылка работает и проблема в
   чём-то другом; строк нет → рассылка мертва, и маршрут через неё закрыт.
2. **Вызывается ли `update` биндера у артефакта в инвентаре.** Добавить в

   вызывается — это лучший маршрут (раздел 5), не зависящий от реестра.
3. **Звук.** Убрать из `[callbacks]` все ключи, кроме `OnItemDropped`, и
   проверить, останется ли звук при открытии инвентаря.
4. **Что именно ломало контейнеры.** В откаченном состоянии они работают.
   Проверки владения убраны. Больше в них ничего не менять.

## 9. Итог: чего делать НЕ надо (проверенные грабли)

1. **Не вызывать Lua-функции из движковых колбэков конфига** — на этом был

   `m_functor`), поэтому `set_callback` **перезаписывает** предыдущего
   подписчика. На `callback.on_item_take` уже подписан `bind_stalker.script:118`
   (статистика игры) — наша подписка её сломала бы.
3. **Не добавлять проверки владения (`owned_by_actor`) в `on_item_dropped` и
   `take_artifact`** — именно они сломали контейнеры в `33917de`.
4. **Не ссылаться на колбэки, которых в сборке нет** (`actor_item_to_belt`,
   `actor_item_to_ruck`, `actor_on_item_drop`, `actor_on_update` и т.п.) —
   `dynamic_callbacks.lua` их молча игнорирует.
5. **`clamp(val, 0.0f, val)` в `Actor.cpp:2622` — это ограничение СНИЗУ**, не
   сверху. Формула пояса при `boost = 0` сводится к `radiation × condition`.
6. **`boost_radiation_immunity`, `GetRestoreSpeed`, `GetBoostRadiationImmunity`
   из Lua недоступны.** Учитывать их нельзя.
7. **`db.actor.id` — функция.** Сравнивать владение только с `db.actor:id()`.
